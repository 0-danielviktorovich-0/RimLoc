# Translation Memory (TM live) — реализация A+B+C

Дата: 2026-10-05
Ветка: `glm/tm-live`
Статус: реализовано в коде; сравнение с RimTranslate в конце — уровень **DOC_ONLY** (по материалам `docs/development/COMPETITOR_MATRIX.md`, код конкурента в этой сессии не запускался и не читался).

Решение владельца (принято, не меняем): переводная память проекта с тремя путями записи — авто-накопление принятых переводов (A), импорт без слепого доверия (B), ручной CRUD (C). Память — общее состояние канонического проекта, не метаданные RimWorld: живёт в конверте проекта рядом с глоссарием и переживает рестарт.

---

## 1. Маппинг A/B/C на реализацию

| Часть | Где реализовано | Суть |
|---|---|---|
| **A. Авто-накопление** | `crates/rimloc-services/src/session.rs`: сбор в `ProjectSessionManager::apply` (по `IntentAction::SetTranslation` при `applied > before`) → `tm_auto_accumulate()` | Только **ack-нутый** accept (`project_apply_intents` до persist-before-ack). Черновик (простой `Save`/непринятая правка) запись **не** создаёт — покрыто тестом `tm_auto_accumulation_on_accepted_apply_only`. Запись: `provenance=AUTO`, `status=ACCEPTED`. Источник берётся из инвентаря проекта (не из намерения клиента) |
| **B. Импорт** | `session.rs`: `tm_import` → `parse_tm_rows` (`parse_tm_json_rows` / `parse_tm_csv_rows`, свой RFC-4180-lite токенайзер) → `resolve_tm_row` | JSON (массив объектов) или CSV (колонки `source,target[,locale][,status]`). Записи: `provenance=IMPORT`, `status=DRAFT` по умолчанию; явный статус в строке — уважается (это явное намерение пользователя). Битая строка = `rejected` в ответе, батч не проваливается; payload, не парсящийся ни как JSON, ни как CSV, — типизированный отказ `contract_violation` без частичного применения |
| **C. Ручной CRUD** | `session.rs`: `tm_upsert`, `tm_delete`; Tauri-адаптер `contract_adapter.rs`; React `components/Tm.tsx` | `provenance=MANUAL` проставляет сервис (клиент провенанс подделать не может), статус выбирает пользователь, по умолчанию `ACCEPTED`. Ручная правка может и повысить, и понизить статус существующей записи — решает человек. Удаление по стабильному `id`; неизвестный id — типизированный отказ |

Контракт: DTO `TmList/Upsert/Delete/Import/Lookup` + `Capability::TranslationMemory` — `crates/rimloc-services/src/contract.rs`. Домен: `crates/rimloc-domain/src/tm.rs` (`TranslationMemoryEntry`, `TmStatus`, `TmProvenance`, `validate_input`). Tauri: пять команд `project_tm_*` в `CONTRACT_COMMANDS`/`LIVE_COMMANDS` и обоих `generate_handler!`. React: `types.ts`/`transport.ts`/`client.ts` + экран `#/tm`.

## 2. Статусная модель

- Статусы: `DRAFT` < `ACCEPTED` < `REVIEWED` (`TmStatus::rank()` = 0/1/2).
- Приоритет доверия: **REVIEWED > ACCEPTED > DRAFT**. Сильную запись не ослабляет ни один путь записи:
  - авто-накопление: существующую `REVIEWED` не трогает; равную/слабую с другим переводом — перезаписывает принятой человеком версией;
  - импорт: `rank(существующей) > rank(новой)` → `skipped`; равная/слабее → `updated`.
- Провенанс (`AUTO`/`IMPORT`/`MANUAL`) — честная бухгалтерия происхождения; сам по себе доверие не повышает.
- Ключ записи: `(source_text, target_locale)`, регистр значим (`Save` и `save` — разные ключи). `id` стабильный, выдаётся один раз и переживает апдейты.

## 3. Формат импорта

JSON — массив объектов (алиасы `source_text`/`target_text`/`target_locale` принимаются):

```json
[
  {"source": "Save game", "target": "Сохранить игру", "locale": "Russian"},
  {"source": "Load game", "target": "Загрузить игру", "locale": "Russian", "status": "reviewed"}
]
```

CSV — `source,target[,locale][,status]`, опциональная строка заголовка (распознаётся и пропускается), кавычки RFC-4180 (удвоение `""`, запятые внутри кавычек):

```csv
source,target,locale,status
"Save game","Сохранить игру",Russian,draft
"Extra, key","в кавычках, с запятой",Russian,draft
```

Правила: локаль обязательна (без неё строка отклоняется — изоляция локалей делает запись без локали нечестной); `format: json|csv` форсирует формат, иначе авто-детект по первому байту (`[` или `{` → JSON — поэтому битый JSON это отказ, а не мусорная CSV-строка). Ответ несёт счётчики `imported/updated/skipped/rejected`. Валидация каждой записи: лимиты 4000/4000/16 символов, пустые поля и control-символы (C0 + DEL) отклоняются до записи (ревизия не двигается).

## 4. Алгоритм lookup (`tm_lookup`)

1. Изоляция: рассматриваются только записи с `target_locale == locale`.
2. Тиры: **точный** (`source_text == query`) → **нормализованный** (`normalize`: trim, схлопывание пробелов, нижний регистр) → **нечёткий** (собственный DP Левенштейна в двумя строками и ранним отсечением, без новых зависимостей; посимвольно, кириллица считается честно).
3. Порог нечёткости: `max(2, len(нормализованный запрос)/10)` — фиксированный минимум 2 держит короткие UI-строки достижимыми, пропорциональная часть растёт с длиной.
4. Порядок выдачи: тир → дистанция → ранг статуса (REVIEWED > ACCEPTED > DRAFT) → порядок вставки. `limit` по умолчанию 5, зажим 1..=50. В матче возвращаются `match_kind` (какой тир сработал) и `distance` (только для fuzzy).

**Смена исходника (документированный контракт):** запись ключуется текстом исходника, поэтому при изменении исходника старая запись остаётся (стареет), а новый исходник — miss до повторного перевода. Покрыто тестом `tm_source_update_ages_the_old_record`.

## 5. Персистентность

По образцу глоссария: записи живут в `Project.tm` (canonical `Project`, `#[serde(default)]` — старые проекты грузятся с пустой памятью), каждая мутация проходит общий `persist_project_state`: bump ревизии → проверка внешних изменений по хешу → save-before-ack. Упавший save оставляет правку dirty в памяти и не ack-ает. Авто-накопление сворачивается в ту же durable-запись, что и применённые интенты. Перезапустение сессии восстанавливает память (тест `tm_crud_roundtrip_and_restart_persistence`).

## 6. Ограничения

- TM — состояние проекта, а не глобальная база: между проектами память не шарится (осознанно: изоляция таргетов и проектов).
- Порог нечёткости консервативен (`max(2, len/10)`) — редкие дальние совпадения сознательно не выдаются.
- `tm_list`-фильтры — in-memory подстрока/точные совпадения; для десятков тысяч записей индекс не строится.
- Тесты — Rust-модульные (`cargo test -p rimloc-domain -p rimloc-services`: 19 + 224 зелёные, из них 9 тестов TM в domain/session + wire-roundtrip DTO в contract). UI-экран проверен сборкой (`npm run build`), но не прогнан вручную в десктоп-приложении: `cargo check -p rimloc-gui --lib` зелёный, бинарь в этом worktree не собирается из-за предусловия среды (отсутствует `frontend-v2/dist`, воспроизведено на HEAD без правок TM).
- Импорт большого CSV (сотни тысяч строк) — линейный скан с полным upsert-поиском на строку; не профилировалось.

## 7. Сравнение с подходом RimTranslate (compendium/fuzzy) — уровень DOC_ONLY

Ниже — сопоставление по материалам `docs/development/COMPETITOR_MATRIX.md` (строки 15, 57–58); код RimTranslate в этой сессии не читался и не запускался, поэтому всё, что дальше, — пересказ вторичных источников, а не верификация:

- RimTranslate (Python, gettext-нативный PO-цикл) хранит память как **compendium** — PO-файл из чужих переводов, и префилл идёт по `msgctxt`, то есть **по ключу** строки, а не по тексту исходника; найденные соответствия помечаются gettext-флагом `fuzzy` (`RimTranslate.py:271-278` по матрице).
- Наша TM живёт **по паре (текст исходника, локаль)** и не привязана к ключам: переживает смену ключей/структуры мода, но честно миссячит при переформулировке исходника (см. §4). Fuzzy у нас — ограниченный Левенштейн с ранжированной выдачей и статусами доверия; gettext-`fuzzy` у RimTranslate — флаг «проверь человека», без ранжирования и провенанса.
- Итог для кампании: подходы ортогональны — RimTranslate решает префилл внутри PO-воркфлоу по ключам, наша TM решает накопление принятых переводов поверх канонического проекта. Возможная точка роста (DOC_ONLY, не реализовано): экспорт TM-хитов в PO-комментарии с провенансом, где по матрице RimLoc уже единственный с чем-то подобным (`write_po_with_tm`).
