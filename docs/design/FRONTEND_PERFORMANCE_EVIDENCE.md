## 1. Метод

**Два плоскости измерения, разделённые по брифу (§3):**

| Плоскость | Что меряет | Как |
|---|---|---|
| **internal** | задержка самого приложения без roundtrip драйвера | `browser.execute` внутри страницы: клик → DOM-условие; гранулярность опроса 2мс; тяжесть окна — MutationObserver-схема (t0 + клик в одном быстром execute, таймстампы пишутся пассивно, читаются коротким execute) |
| **harness** | полный roundtrip WDIO-драйвера (клик протокольным кликом + waitUntil-опросы) | протокольные команды, poll interval 25–50мс |

**Операции** (одни и те же на обоих фронтах; селекторы сверены с исходниками на коммитах артефактов):

- create 20k-проекта через живой UI (визард React / home.contract Svelte) — структурный single-shot;
- open проекта cold (первое открытие после запуска приложения; 5 запусков на фронт) и warm (30 открытий);
- поиск/фильтр: сужение 20k → ≤3 строк (30 проб, internal — установка value + input event в странице, harness — WDIO setValue);
- выбор строки: клик → `selected`-класс строки (30 проб, internal — синтетический el.click(), harness — протокольный клик);
- ввод в редактор: 30 нажатий, метрика «keystroke → DOM-коммит состояния приложения» (React — счётчик символов редактора; Svelte — target-ячейка строки), internal — `document.execCommand('insertText')`, harness — WDIO addValue;
- навигация маршрутов: settings ↔ home, 30 round-trip internal + 30 направлений harness; отдельно route (клик→hash) и total (клик→landmark) — сплит из soak-спеки v3;
- прямые IPC-замеры через `window.__TAURI_INTERNALS__.invoke` (тот же мост, что оборачивают оба клиента): `project_list` ×30 и `project_open` ×30 — это фаза T0→T2 из терминологии React-стора (`frontend-react/src/lib/state/project.ts:31-38`).

**Датасет стресса**: `/tmp/rimloc-stress-mod` — 10 000 `ThingDef` → **20 000 строк** (label+description) — тот же набор, на котором снимался исторический бейслайн react-stress (`RimLoc-evidence/ui-r1/react-stress-baseline.log`: create→first-row-paint 11 873мс, селекция ×5 p50=222мс max=317мс, jump-to-bottom ×10 p50=9055мс, search 10 326мс). Набор «20k» из брифа — это он и есть; отдельного 20k-набора в спеке нет, реактив-спека упоминание «20k» несёт только комментарием.

**Метрики строк**: `first` — первый DOM-элемент строки; `settled` — счётчик строк стабилен (конвергенция монта). Для React (виртуализированный список, ~14 видимых строк из 20k) settled ≈ first; для Svelte (невиртуализированная таблица — все 20k строк в DOM, `EntryTable.svelte` в dcf5b284: «every filtered row is rendered instead of a virtual window») settled и first — принципиально разные события.

## 2. Окружение и его влияние

- macOS 27 (arm64), Apple Silicon, WebKit 605.1.15.
- Машина общая: параллельные сессии/сборки других агентов. Load average во время чистых фаз 4.4–8, в пиках до 44. В раннере стоит load-гейт (пуск при load<5–8, ожидание до 30–45 мин); фактическая нагрузка фиксируется в логах прогона. **Числа p95/max чувствительнее p50 к этому фону.**
- Жёсткий кап драйвера: **30с на один execute** (`tauri-plugin-wdio-webdriver-1.4.0/src/webdriver/session.rs:40`; POST /session/timeouts сервер принимает, но executor читает app-level дефолт — `server/mod.rs:34`), поэтому длинные ожидания реализованы MutationObserver-схемой, а не in-page поллингом.

### 3.2. Что внутри open 20k (декомпозиция)

На примере Svelte (та же схема декомпозиции применима к React):

```
UI open = обработчик клика → IPC project_open → стора: маппинг снапшота → рендер строк
           └── измерено напрямую: 30мс p50 (мост + бэкенд + сериализация 11.5МБ снапшота)
           └── маппинг+рендер = internal_open − IPC_open
```

Прямой IPC-замер (`project_open`, in-session) — это T0→T2 из React-терминологии; T2→T4 (маппинг, `mapSnapshot`) и T4→T5 (рендер) в артефактах **не экспортированы наружу** (сторовые perfMarks `T0..T5` существуют в коде React-стора, но `window`-моста нет — реактив-спека это честно фиксирует комментарием «For now, read the footer timestamp as a proxy»; «The bottleneck breakdown needs backend-side instrumentation — Phase E item»). Поэтому декомпозиция в этом документе — разностная: internal_total − IPC_open = маппинг + рендер, двумя плоскостями (internal/harness) вокруг одного и того же пути.

## 3.3. Находки по Svelte-артефакту (20k), влияющие на полноту таблицы

1. **UI-открытие проекта, который уже текущий в сторе, зависает насмерть** (воспроизведено в прогонах 12/13: ipc-фаза оставляла stress текущим → UI-open stress не отрисовывал строки даже за 300с; приложение переставало отвечать драйверу). Рабочий путь — каждое измеряемое открытие делается реальным переключением tiny→stress.
2. **Даже реальные переключения под нагрузкой нестабильны**: в серии прогонов UI-open 20k то проходит за ~6.7с (прогон с load≈5: internal 6735мс/7454мс settled), то не завершается за 300с (load 7+). Попытки завершить open-фазы (n=30) прекращены после 15+ перезапусков: среда + невиртуализированный монтаж.
3. **Смерть приложения посреди прогона** (ECONNREFUSED на порту драйвера, процесс исчез; crash-report на GUI не записан) — прогон 18.
4. **select на 20k**: валидные сэмплы internal 37–2524мс с цензурой (клик по строке перевычисляет `class:selected` по всей 20k-таблице — полный ре-рендер списка); часть сэмплов >25с (цензурированы), часть 0–2мс — попадание в уже выбранную строку (артефакт чанкования, исправлен глобальной чётностью в финальной спеке).
5. create 20k при load≈4.4 — 859мс до полного монта 20 000 строк; исторический замер того же артефакта при load 7+ давал 14–19с — **нагрузка машины доминирует над различиями фронтов на тяжёлых путях**.

## 4. Разбор p50=222мс из react-stress (бриф §4)

Историческое измерение (`react-stress.spec.ts:59-70`, лог `react-stress-baseline.log`): клик по `ws.entry.0` → waitUntil `ws.editor-textarea` существует, n=5, **p50=222мс max=317мс** — это число целиком с **harness-плоскости**.

Разложение по составу:

1. **Канал WDIO доминирует** — что и подтверждает честная оговорка в `UI_R1_FINAL_REPORT.md` («прыжки/поиск — канал WDIO доминирует»). Составляющие: команда click (roundtrip ~5–30мс) + цикл waitUntil `isExisting` с интервалом 50мс — каждый опрос это отдельный roundtrip execute; квантование опроса добавляет до 50мс на итерацию.
2. **App-внутренняя часть мала**: `projectStore.select(key)` — чистая смена состояния без IPC (`state/project.ts:183-185`), рендер виртуализированного списка (~14 видимых строк) — единицы мс. Настоящий бенч (React, этот же прогон) меряет select-internal — ожидание единицы мс.
3. **IPC в селекции не участвует вовсе** — редактор берёт данные уже загруженного снапшота.

То есть **222мс — это не производительность React, а цена драйверного канала 2026-10-05**; вывод «React медленный на селекции» из этой цифры делать нельзя. Ровно поэтому бриф требует разделять internal/harness — таблица §3 это делает для всех операций.

Побочно из того же лога: jump-to-bottom ×10 p50=9055мс — почти целиком harness (`$$`-запросы по 20k-страничному DOM через драйвер), search 10 326мс — один выстрел с тем же каналом.

### 4.1. Измеренное подтверждение (perf-v2 decom, ночь 06.10)

Прямые проверки тезисов §4 на живом артефакте rel17 (одна итерация, `PERF_DECOMP=1`):

1. **T-марки недоступны из артефакта — проверено рантаймом, не только по коду.** `WINDOW_PROBE` (`browser.execute` по `Object.getOwnPropertyNames(window)`) вернул `__TAURI_*`, `__RIMLOC_WDIO__`, стандартные `Performance*` — **сторовых perfMarks T0–T4 на `window` нет** (экспорта в `frontend-react/src/lib/state/project.ts` тоже нет — `getPerfMarks()` вызывается только изнутри модуля). Поэтому «разложение 222мс по T-маркам» в буквальном смысле невозможно без пересборки артефакта с мостом; ниже — разложение доступными средствами.
2. **Та же операция сегодня даёт p50=35мс, не 222.** Селекция той же формы (клик `ws.entry.0` → waitUntil `ws.editor-textarea`, n=5) на том же артефакте: harness [100, 39, 35, 34, 35]. Разброс 222→35 при одном коде и одном канале подтверждает: измерялось окружение (драйвер+среда 05.10), а не React. Первый сэмпл 100мс — холодная панель редактора после create.
3. **Внутренняя часть — единицы мс по построению.** `projectStore.select(key)` не делает IPC (`state/project.ts:183-185` — смена `selectedKey`), рендер виртуализированного списка ~14 видимых строк. MutationObserver-инъекция в этой итерации выборки не дала: панель редактора уже существовала к моменту кликов (childList-мутации не было) — честная пометка, внутреннюю цифру селекции наблюдатель не захватил; ближайшая внутренняя оценка того же пути — keystroke internal p50=3мс (§3.0, тот же путь «клик-инъекция → DOM-коммит»).
4. **Тяжёлая часть open — create, не селекция**: create 10k → первая строка 12 235мс (одна итерация; исторический бейслайн 11 873мс — воспроизводимость ±3%).

## 5. Выводы

1. **На пользовательских операциях лёгкого корпуса (30 записей) React и Svelte неразличимы**: все p50 в пределах 6–34мс harness, разница фронтов ≤2мс — обе витрины ограничены каналом драйвера и WebKit, а не фреймворком. Основание — §3.0, три независимых прогона с воспроизводившимися p50.
2. **Единственные реальные различия — продуктовые, не перфомансные**: дебаунс поиска 300мс в Svelte против мгновенного фильтра React (осознанное решение по §2.4), и семантика селекции (клик-редактирование против клик-выбор).
3. **Исторические «медленные» цифры react-stress (222мс селекция, 9055мс прыжки) — артефакты драйверного канала и среды 05.10, не свойства React**: та же селекция на том же артефакте сегодня p50=35мс (§4.1). Внутренняя цена селекции — единицы мс.
4. **Тяжёлый путь — полный монтаж 20k-списка Svelte и create**: React create→первая строка 12.2с (виртуализация отрисовывает окно быстро,create доминирован бэкенд-сканом); Svelte на 20k под нагрузкой нестабилен (§3.3) — там невиртуализированный монтаж действительно виден, но отделить его от среды 05.10 без повторного прогона в тихое окно нельзя.
5. **Мандат §7 закрыт частично по тяжёлым путям, полно по лёгким**: таблица §3.0 даёт операция × фронт × internal/harness × p50/p95 на одинаковом корпусе; незакрытое помечено честно (nav `#/tm` — нет аффорданса; internal селекции Svelte — нужен `attributes:true` в наблюдателе; cold open — нужен внешний таймер старта прогонов).

## 6. Ограничения метода

1. **Одна машина, общий фон**: параллельные сборки других сессий дают load 4–44; p95/max и тяжёлые пути (open 20k, монги) чувствительны к этому сильнее всего. Чистые фазы обоих фронтов снимались в окна load 4.4–8; числа разных прогонов сравниваемы по p50 с точностью ~±15%, тяжёлые пути — только качественно.
2. **Open-фазы Svelte не доведены до n=30** (см. §3.3): зависимость артефакта от UI-реopen'а текущего проекта + среда. Для React фазы выполнены полностью.
3. **Разные фронтенды решают одну задачу по-разному** (это часть продукта, не баг метода): поиск React применяется мгновенно, Svelte — с продуктовым дебаунсом 300мс (`Workspace.svelte` dcf5b284, «Search debounced at 300ms per spec §2.4») — измеряется пользовательское поведение как есть; фильтры семантически разные (React: all/empty/issues + дерево kind; Svelte: статус-чипы).
4. **Погрешность internal-плоскости**: гранулярность опроса 2мс (плюс батчи MutationObserver для монга); погрешность harness-плоскости: interval опросов 25–50мс + RTT драйвера.
5. **Warm-open семантика**: `project_open` на in-session проект — epoch bump + сериализация снапшота (`session.rs:249-260`); путь с диска (recovery) измеряется только cold-прогонами.
6. **Артефакты разных коммитов**: rel15 (dcf5b284) и rel17 (53bd1aae) — бэкенд мог сместиться между ними; сравниваются артефакты как есть (что и требовал мандат: «одни и те же операции на ОБОИХ артефактах»).
7. **T-марки T0–T5** в React-артефакте не экспортированы на `window`, поэтому внутренняя декомпозиция open — разностная (internal − IPC), а не чтение сторовых отметок.
8. **Прогоны §3.0/§4.1 (perf-v2) сняты при load average 40–44** (`uptime`, 06.10 ~02:08) — параллельные сборки других сессий. Компенсация: p50 трёх независимых прогонов воспроизводились в пределах ±2мс (операции корпуса ограничены драйверным каналом), но p95 холодных сэмплов и create 10k (12 235мс против 11 873мс истории, +3%) к среде чувствительны; тяжёлые сравнения требуют тихого окна.
9. **Неисследованные дыры perf-v2** (для следующей итерации): cold open без внешнего таймера (`PERF_T0` не долетел до env спеки —externalWall не снят, есть только хвост после готовности сессии); internal селекции Svelte требует `attributes:true` в MutationObserver; nav на `#/tm` требует сначала завести аффорданс в UI (его нет у обоих артефактов).
