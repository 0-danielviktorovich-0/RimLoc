# GUI Design Spec — Svelte 5 GUI для RimLoc

**Статус**: дизайн-фаза, утверждения не реализованы · **Дата**: 2026-09-24 (IA дополнена, §7–§24) · **Стек**: Svelte 5 (runes) + Tauri 2
**Методология**: скилл ui-ux-pro-max — дизайн-система «Minimalism & Swiss Style» (density 8/10, motion 2/10, variance 3/10), палитра slate, IBM Plex Sans + JetBrains Mono. Адаптация: зелёный из выдачи скилла отдан статусу «переведено», primary-действие — индиго, чтобы цвет действия и цвет статуса не конфликтовали.

---

## 1. Дизайн-токены

### 1.1 Тема

Три режима: `light` / `dark` / `system`. Реализация — атрибут `data-theme="light|dark"` на `<html>`; при `system` — трекинг `prefers-color-scheme`. Инлайн-скрипт в `index.html` выставляет тему до первой отрисовки (без вспышки светлой). **Тёмная — по умолчанию** (десктопный инструмент; «dark primary» означает только первичный референс/дефолт — продукт НЕ dark-only: light и system/Auto — полноправные темы, каждая проверяется на контрасты). Выбор сохраняется в локальных настройках GUI (не в бэкенде).

### 1.2 Цвета — CSS custom properties

Объявляются на `:root` (light) и `[data-theme="dark"]`; компоненты используют только переменные, сырой hex — запрещён.

```css
:root {
  --color-bg: #F8FAFC;            --color-fg: #0F172A;          /* контраст 16.9:1 */
  --color-surface: #FFFFFF;        --color-surface-fg: #0F172A;
  --color-muted: #F1F5F9;          --color-muted-fg: #475569;    /* 7.0:1 */
  --color-border: #E2E8F0;         --color-border-strong: #CBD5E1;
  --color-primary: #4F46E5;        --color-primary-fg: #FFFFFF;  /* 6.3:1 */
  --color-primary-hover: #4338CA;
  --color-focus-ring: #2563EB;     --color-destructive: #DC2626;
  --color-status-untranslated: #B45309;  --color-status-translated: #15803D;
  --color-status-todo: #1D4ED8;          --color-status-source-changed: #C2410C;
  --color-status-pending-review: #6D28D9; --color-status-orphan: #64748B;
}
[data-theme="dark"] {
  --color-bg: #0F172A;             --color-fg: #F8FAFC;          /* 17.1:1 */
  --color-surface: #1B2336;        --color-surface-fg: #F8FAFC;
  --color-muted: #272F42;          --color-muted-fg: #94A3B8;    /* 7.4:1 */
  --color-border: #334155;         --color-border-strong: #475569;
  --color-primary: #6366F1;        --color-primary-fg: #FFFFFF;

```

Статусы — **точка/иконка цвета статуса + нейтральный текст и число**; цвет никогда не единственный носитель смысла (WCAG 1.4.1). Все пары «fg на bg/surface» ≥ 4.5:1, крупный текст ≥ 3:1.

### 1.3 Типографика

| Токен | Значение | Применение |
|---|---|---|
| `--font-ui` | `"IBM Plex Sans", system-ui, sans-serif` | весь UI; woff2 бандлится в приложение (офлайн-инструмент, без CDN) |
| `--font-mono` | `"JetBrains Mono", monospace` | TKey-пути, имена файлов, XML, коды ошибок |
| `--text-base` | 14px / line-height 1.5 | основной UI |
| `--text-dense` | 13px / 1.45 | таблица workspace |
| `--text-meta` | 12px / 1.4 (минимум) | счётчики, provenance |
| `--text-heading` | 18–20px / 600 | заголовки экранов |

Кириллица — обязательное требование к гарнитурам (IBM Plex Sans и JetBrains Mono её покрывают полностью).

### 1.4 Spacing, радиусы, движение

- Spacing-шкала (плотный дашборд, base 4px): `--space-1: 4 · --space-2: 8 · --space-3: 12 · --space-4: 16 · --space-6: 24 · --space-8: 32`.
- Радиусы: `--radius-sm: 4px` (чипы, инпуты) · `--radius-md: 6px` (кнопки, карточки) · `--radius-lg: 10px` (модалки, панели).
- Движение: hover/фокус 150–200ms `ease-out`; открытие панелей/модалок 200–250ms; **без** анимации длинных списков и таблиц. `prefers-reduced-motion: reduce` → все переходы ≤ 1ms.
- Цели клика ≥ 32×32px (десктоп), между интерактивами ≥ 8px. Иконки — SVG (Lucide), эмодзи как иконки запрещены.

## 2. Информационная архитектура и экраны

### 2.1 Карта

```
Home ──(новый мод)──► Onboarding (4 шага) ──► Translator Workspace ◄──(существующий)── Home
                                Workspace ──► Результаты (Валидация / Сборка / Сравнение)
```

Глобальная шапка: имя проекта, целевая локаль, переключатель темы, язык интерфейса. Back-поведение предсказуемо: из Workspace в Home — через явную кнопку «Закрыть проект» (с подтверждением при несохранённых правках), не через «назад» ОС.

### 2.2 Home — два равноправных входа

Два workflow разной природы, поэтому **две карточки равного веса** (не «главная кнопка + вторичная ссылка»):

1. **«Перевести новый мод»** — путь новичка: выбор папки мода → onboarding-мастер.
2. **«Открыть существующий перевод»** — путь продолжающего: выбор файла проекта перевода (или недавних) → сразу в Workspace.

Раскладка: две карточки 1:1 по ширине, равная высота, иконка + заголовок + одна строка описания. Под ними — список «Недавние проекты» (если есть): имя мода, локаль, дата, % готовности, клик → Workspace. Пустое состояние без недавних — список не рендерится.

### 2.3 Onboarding «Translate a mod» — 4 шага, progressive disclosure

Мастер-визард, показываем только текущий шаг + прогресс-индикатор; на каждом шаге одна задача и один главный ответ.

| Шаг | Экран | Действие пользователя | Сервис-вызов (контракт) |
|---|---|---|---|
| 1 | «Выберите мод» | путь к папке мода (диалог ОС) + превью: имя, версии, найденные Defs | `scan(mod_root)` |
| 2 | «Язык перевода» | выбор целевой локали из списка | — |
| 3 | «Что переводим» (свернуто по умолчанию) | фильтры объёма: категории записей (Keyed / DefInjected / TKey / Strings / Backstories), «только непереведённое»; предустановка «всё» | eligibility-подсказки от сервиса |
| 4 | «Готово» | сводка (мод, локаль, счётчики по категориям) + «Создать проект и открыть редактор» | `create_project(...)` |

Назад/Далее доступны всегда; шаг 3 можно не открывать вовсе (progressive disclosure: по умолчанию он свёрнут в «Дополнительные настройки»). Ошибки сканирования показываются на своём шаге, мастер не закрывается.

### 2.4 Translator Workspace — ядро приложения

Трёхпанельный layout (при < 1100px панель контекста уходит в выдвижную нижнюю половину):

- **Слева (240px)**: навигатор по мод-структуре — дерево категорий/файлов записей; выбор фильтрует таблицу.
- **Центр (гибкий)**: таблица **SOURCE | TARGET**.
- **Справа (320px)**: панель контекста выбранной записи.

**Таблица**: десятки тысяч строк → **виртуализация обязательна** (только видимое окно + overscan 8, фиксированная высота строки 40px). Колонки: статус-точка · SOURCE (en, mono для TKey-семейства, нередактируемо) · TARGET (редактируемо) · признак «изменён источник». Сортировка по статусу/алфавиту; поиск по source/target — debounce 300ms.

**Фильтры статусов** — чипы над таблицей с живыми счётчиками, мультивыбор: `untranslated` / `translated` / `todo` / `sourceChanged` / `pending_review` / `orphan`. Счётчик пересчитывается сервисом, не клиентским обходом.

**Инлайн-редактирование**: двойной клик или Enter по строке → ячейка TARGET в режим ввода. `Enter`/`Ctrl+Enter` — сохранить, `Esc` — отменить, `Tab` — к следующей untranslated-строке (главный цикл работы переводчика). Сохранение — **только через** `update_translation(entry_id, locale, text)`; оптимистичный апдейт UI + бейдж «сохраняется…» до подтверждения сервиса; конфликт (источник изменился во время правки) — не молча, а диалог. Черновик несохранённой правки виден в ячейке курсивом до коммита.

**Панель контекста**: заголовок записи (defName + TKey-путь, mono), **все мульти-контексты TKey** списком: источник узла, файл + строка, значение источника, sibling-текст для ориентира. Ниже — provenance (origin: human/TM/LLM/imported), дата правки, поле «Заметка переводчика», кнопки «Отметить как переведено/на проверку».

### 2.5 Результаты — Validate / Build / Compare

Один экран «Результаты» с тремя вкладками, каждая — свой сервис:

- **Валидация**: список проблем, сгруппированных по типу правила; клик по проблеме открывает запись в Workspace; фильтр по severity; пустое состояние «Проблем не найдено» — зелёная подтверждая-строка, не пустота.
- **Сборка**: параметры (формат вывода, путь), кнопка «Собрать»; прогресс-бар с фазами; по завершении — путь к артефакту (mono, кнопка «Открыть папку») + лог сборки в сворачиваемом блоке.
- **Сравнение**: diff источника против текущего/предыдущего перевода или между версиями проекта; построчный diff (добавлено/удалено/изменено) с легендой, для длинных записей — свёртка.

## 3. Состояния и принципы

**Каждый экран и каждая область данных имеют все три состояния, и они проектируются явно:**

| Состояние | Правило |
|---|---|
| Loading | скелетоны (таблица: 8 строк-заглушек), ни в коем случае не блокировка всего окна; отмена операции доступна |
| Empty | осмысленный текст + следующий шаг («Модуль не выбран — выберите категорию слева»), не просто пустой div |
| Error | человекочитаемое сообщение (i18n) + код + кнопка «Повторить»; raw-ошибка бэкенда — в сворачиваемых деталях |

**Принципы:**

1. **Сервис-граница.** GUI не знает про PO и внутренние представления. Единственная операция записи переводов — `update_translation(entry_id, locale, text)`; чтение — через сервисы (scan/project/list_entries/list_translations/validate/build/compare). Внутренние структуры бэкенда заморожены: GUI-слой изолирует их за сторами (Svelte 5 runes: `$state`/`$derived`), чтобы изменения бэкенда не трогали компоненты.
2. **Mock-based разработка разрешена**: UI собирается против MockProvider (тот же acceptance-контур, что `scan→project→MockProvider→validate→build` в плане); контракт сервисов — единственная точка стыковки.
3. **Никаких потерь**: несохранённая правка не может исчезнуть молча (закрытие проекта, смена фильтра, краш → восстановление черновика).
4. **Прогрессивная плотность**: новичку видны 2 кнопки в тулбаре; продвинутые действия (заметки, provenance, массовые операции) — во вторичных меню.

## 5. Семантическая автоматизация (под будущий tauri-driver E2E)

Каждый интерактивный элемент обязан иметь: корректный **role**, стабильное **accessible name** и **data-testid**. E2E-локаторы — по приоритету: accessible name (en-локаль в тестах) → role+name → data-testid; CSS-селекторы по классам запрещены.

| Элемент | Role | Accessible name (источник) | testid-конвенция |
|---|---|---|---|
| Вход Home | `button` | из `home.newTranslation.title` / `home.existing.title` | `home.entry-new`, `home.entry-existing` |
| Шаг мастера | `button` («Далее»/«Назад») + `aria-current="step"` на шаге-индикаторе | i18n шага | `onboarding.next`, `onboarding.back` |
| Чип фильтра статуса | `button` + `aria-pressed` | «Фильтр: Не переведено, 1234» (имя без числа в стабильной части: label из i18n, счётчик — в отдельной ноде) | `workspace.filter.<status>` |
| Строка таблицы | `row` внутри контейнера `grid`; виртуализация не должна ломать семантику: контейнер объявляет `aria-rowcount` (реальное число записей), видимые строки — `aria-rowindex` | имя строки = defName/TKey записи | `workspace.row.<entry_id>` |
| Ячейка TARGET в редактировании | `textbox` с именем колонки «Перевод» + `entry_id` в `aria-describedby` контекста | i18n колонки | `workspace.editor.<entry_id>` |
| Панель контекста | `region` + `aria-label="Контекст записи"` | фиксированная i18n-метка | `workspace.context` |
| Вкладки результатов | `tablist/tab/tabpanel` | i18n вкладок | `results.tab-validate` и т.д. |
| Иконные кнопки (закрыть, копировать путь) | `button` + явный `aria-label` (иконка `aria-hidden`) | i18n | `common.close` и т.д. |

Требования к среде: безразличие к локали тестов достигается фиксированной en-локалью в CI-профиле; динамические части (счётчики, даты) — в отдельных дочерних нодах, чтобы name-локатор был стабильным.

## 6. Открытые вопросы — классификация и решения (24.09)

| # | Вопрос | Классификация | Решение |
|---|--------|---------------|---------|
| 1 | Полный набор статусов (6 чипов vs размерности OBSOLETE/AMBIGUOUS/INVALID) | **BACKEND BLOCKER** — модель статусов замораживается в Mandate 2 (Gate I) | v1 строит чипы из сервисного перечня (не хардкодом): сейчас 6 статусов из ТЗ, при расширении модели UI подхватит без ломки |
| 2 | Автосохранение vs явный коммит `update_translation` | **AUTONOMOUS REVERSIBLE DEFAULT** | Debounce 800ms после паузы ввода + явный dirty-индикатор + flush при потере фокуса/навигации/закрытии; черновик переживает краш (draft в локальном состоянии проекта). Легко поменять на explicit-save, если пользователя не устроит |
| 3 | TM/LLM-подсказки в Workspace v1 | **AUTONOMOUS REVERSIBLE DEFAULT** | TM-prefill подсказка — в v1 (данные уже есть, нулевая стоимость); LLM-кнопка — в v1 за MockProvider (acceptance-контур), обе деградируют в чистое no-provider состояние без ошибок |
| 4 | Undo в редакторе | **AUTONOMOUS REVERSIBLE DEFAULT** | Локальный per-entry undo-стек в v1 (в рамках сессии редактора); проектная история/журнал — позже, за сервисной границей |
| 5 | Шрифты: бандл vs системный стек | **AUTONOMOUS REVERSIBLE DEFAULT** | Бандлить IBM Plex Sans + JetBrains Mono (полные кириллические наборы): офлайн-инструмент без сетевых зависимостей + детерминированный рендеринг для скриншотных E2E. Цена ~сотни КБ приемлема |

Ни один вопрос не требует остановки кампании; пересмотр дефолтов #2–#5 — рутинная правка.

## 7. Режимы перевода — пять источников, одна модель

Все режимы работают над одной канонической моделью Project (Gate I: три workflow делят одну бизнес-логику). Режим определяет, **кто пишет черновик TARGET**, а не путь записи: валидация, provenance, сборка — общие.

| Режим | Что это | Кто пишет TARGET | Статус после |
|---|---|---|---|
| **Manual** | редактирование в Workspace | человек | `translated` / `pending_review` |
| **TM & существующие знания** | TM, глоссарий, чужие паки, импорт существующего перевода | детерминированный матчёр/импортёр | `translated` (origin=TM/Imported) |
| **Integrated AI** | настроенный провайдер (§12) | AI по конвейеру §8 | `needs review` |
| **External AI** | ChatGPT/Claude/GLM в вебе, без API-ключа (§10) | пользователь переносит батч | `needs review` после импорта |
| **AI Agent** | CLI/MCP-агент ведёт прогон через те же сервисы | агент | `needs review`; будущее |

Режим выбирается **на прогон**, не на проект: комбинирование легально и типично (TM-prefill → AI → review). Смена режима не трогает историю и статусы уже принятых записей.

## 8. AI — черновик до верификации

Единый конвейер для Integrated AI, External AI и Agent:

`source → context (usages, sibling) → glossary/TM → AI-черновик → детерминированная валидация → опциональный AI-review/repair → human review → accepted`

Инварианты:

- AI **никогда** не пишет напрямую в «переведено»: финальное слово всегда за человеком (human review).
- **Provenance обязателен** на каждой записи: origin (human/TM/LLM/imported), модель, время; AI-запись никогда не помечается `human-reviewed`.
- Repair чинит только то, что упало валидацией, и после правки снова проходит ту же валидацию — не «сам себе судья».
- Глоссарий и защищённые записи — приоритет контекста: подаются модели на вход и проверяются детерминированно на выходе.

## 9. Quality-режимы

Пресеты для пользователя; модельные параметры (модель, temperature, число попыток) — в Advanced, не на главном пути.

| Режим | Что делает | Когда выбирать |
|---|---|---|
| **Draft (FAST)** | TM + AI-черновик, валидация плейсхолдеров | быстро посмотреть объём и качество материала |
| **Quality** (дефолт) | + полный детерминированный QA, repair по провалам | обычная работа |
| **Maximum** | translate → validate → reviewer → repair → QA | финальный прогон перед сборкой |
| **Suggest-only** | AI ничего не применяет — только подсказки в SUGGESTIONS (§20) | осторожный режим, обучение, чужой стиль |

Прогон Draft помечается бейджем «черновик», чтобы его результат не спутали с финальным качеством.

## 10. External AI workflow — без API-ключа

Путь для пользователя, который работает с ChatGPT/Claude/GLM через веб-чат: **выбор записей → «Translate with external AI» → батч → Copy/Export → свой чат → Import → маппинг → валидация**. Никакого построчного копирования.

- **Батч** (структурированный, самодостаточный): source/target locale, версия RimWorld, entry ID, EntryKind, текст, контекст записи, глоссарий, TM-примеры, перечень плейсхолдеров, правила синтаксиса грамматики.
- **Copy/Export** — два эквивалента: копируемый промпт (готовый к вставке в чат) и versioned JSON (`schema_version`, формат I3).
- **Import** маппит ответы по **стабильным entry ID**, не по порядку строк; непереведённое и сломанное остаётся в исходном статусе (`preserved`), проблемы — в очередь §11 с подсветкой причины.

## 11. Review queue

После любого автопрогона (Integrated/External/Agent/TM) — очередь «Review problems», отсортированная по severity:

`placeholder mismatch` → `glossary violation` → `подозрительный untranslated` → `ambiguity` → `WordInfo` → `semantic concern`.

Статусы записей после прогона: `translated` / `validated` / `needs review` / `failed` / `preserved` (защищённое или не тронутое). Каждая проблема кликабельна → запись в Workspace с подсвеченной причиной; «принять / исправить / отклонить» — прямо из очереди, без блуждания по таблице.

## 12. Provider manager и Zero-API

Провайдеры: **OpenAI-compatible / Z.AI / Anthropic / Ollama** (локально). Карточка провайдера: статус, модель, connection test, ключ в Keychain (никогда не отображается — только «заменить»), base URL, явные пометки приватности (куда уходят данные) и стоимости.

**Zero-API**: ни одного настроенного провайдера — продукт полноценен: manual + TM + существующие переводы + PO + validate + build работают полностью офлайн. AI — усиление, не зависимость; все AI-точки UI деградируют в чистое no-provider состояние без ошибок.

## 13. Cost UX

Перед большим платным прогоном — **оценка** (записей × токены ≈ стоимость, по тарифу провайдера) и явное подтверждение; **без одобрения платные запросы не отправляются**. Прогресс показывает израсходованное; отмена доступна в любой момент. Локальные и офлайн-операции стоимости не имеют и не спрашивают.

## 14. Quick Translate wizard — 6 шагов

Канонический путь «мод → проверенный перевод»; поглощает onboarding §2.3 (шаги 1–2 совпадают, «Что переводим» уходит внутрь шагов Content/Advanced).

| Шаг | Содержание |
|---|---|
| 1 Content | что переводим (content types §15) + фильтры объёма |
| 2 Languages | целевая локаль (и вторая, если нужна) |
| 3 Method | режим перевода §7 + quality-режим §9; Advanced свёрнут |
| 4 Preflight | скан, счётчики по категориям, совпадения glossary/TM, оценка стоимости при AI — «Начать» |
| 5 Progress | фазы конвейера, отмена, остаток/скорость |
| 6 Review | очередь §11; выход из мастера — только осмысленным следующим шагом (§21) |

**Агрессивные безопасные дефолты**: Advanced свёрнут, весь путь проходится «Далее → Далее → Начать»; всё, что может стоить денег или переписать работу, всплывает до запуска (preflight), не после.

## 15. Content types и Home

Пять типов контента: **Mod · Existing translation · Base game · DLC · Language pack**. «Перевести новый мод» — главный ярлык Home (частый случай); остальные типы — в расширенном создании проекта («Другое» → выбор типа), не вторым равным входом.

Уточнение §2.2 для вернувшегося пользователя: Home — недавние проекты + прогресс по каждому + «Продолжить». **Без метрик-дашборда**: счётчики статусов живут в проекте, не на домашнем экране.

## 16. Workspace navigation

Навигация проекта — пять табов: **Editor / Review / Glossary / TM / Project**. Глобальные действия всегда на виду: **Validate · Compare/Update · Build**. Пользователь в любой момент видит: **где он** (активный таб + фильтр), **сколько осталось** (счётчики статусов), **что дальше** (CTA §21).

**§27.** Техническая структура (Keyed/DefInjected/TKey, файлы) — **не главная навигация новичка**: по умолчанию навигатор группирует записи по смыслу для пользователя (интерфейс, предметы, растения, диалоги…), техтипы и файловое дерево — переключатель «Advanced/Structure» в навигаторе.

## 18. Command palette — Cmd/Ctrl+K

Мост power-user'а и механизм parity с CLI: open project, translate, validate, build, compare, source update, WordInfo, diagnostics, settings, переход по записям. Палитра покрывает действия, которым не место в тулбаре; каждый элемент — тот же контракт доступности и тестидов (§5).

## 19. Capability parity с CLI

Всё человечески-значимое из CLI достижимо из GUI — продуктовым языком, не 1:1 флагами: scan, translate, validate, build, compare, update-source, WordInfo, doctor — есть в GUI. Внутренние флаги отладки и автоматизации — нет: они остаются CLI. Parity-чеклист сверяется перед каждым релизом GUI.

## 21. First-workspace coach и next-action CTA

Первый вход в Workspace — 4 ненавязчивые подсказки (фильтры-чипы, инлайн-редактирование, Tab-цикл по untranslated, review-очередь), skippable, повтор из Help → «Показать подсказки».

Кнопка главного действия всегда называет следующий шаг, а не «Готово»: перевод завершён → **Validate**; валидация чистая → **Build**; источник изменился → **Review changes**; есть проблемы → **Review issues**.

## 22. Звуки и уведомления

Опциональны, дефолт консервативен (тихо). Звук — только значимые события: прогон завершён, найдены проблемы, сборка готова. Тумблер в Appearance; системные уведомления ОС для длинных фоновых прогонов — opt-in.

## 23. §24–25. Визуальные направления — темы над одной IA

Четыре направления (Precision / Aurora / Workshop / Editorial, `GUI_DESIGN_TOKENS.md`) — **темы и характер над одной информационной архитектурой**: эта спека фиксирует фичи и поведение; направления меняют только semantic-слой токенов («кожу»), не геометрию и не IA. QA стиля не имеет права менять поведение.

Рекомендация-кандидат — гибрид **«Precision-Workspace + Aurora-Home + Editorial-типографика SOURCE|TARGET»** — находится **на рассмотрении владельца** (USER PRODUCT DECISION), это не выбор по умолчанию. Прод-дефолт до решения — precision/indigo/comfortable.

## 24. §28. Имплементация против моков

GUI-слой строится против MockProvider и адаптеров (сервисная граница §3.1) **до фриза бэкенд-контрактов (Gate I/J/K)**. Всё из §7–§13 — providers, review queue, external AI — реализуется на моках в том же acceptance-контуре; реальная привязка — после фриза, без переписывания UI.
