# Competitor Matrix — implementation/design level (v2)

Цель документа — зафиксировать не «какие функции есть у конкурентов», а **как именно** они реализованы на уровне кода и данных, и использовать это как проектный материал для RimLoc: что adopt/adapt/combine/reject и где RimLoc может сделать **лучше**, а не паритет. Переработка v1 (список фич) в implementation/design matrix по §5 спецификации кампании.

## Методология

- **Дата**: 2026-09-23. Ревизия v2: все механизмы перепроверены по исходникам; колонка «RimLoc current» перепроверена по коду (в т.ч. закрытые в И1–И2 гэпы — `translate` уже существует).

- **Клоны** (`~/Developing/_competitors-rimloc/`), исходники прочитаны:

**7 вопросов — извлечение.**
- *A1*: как решено — type-package/правила/списки; почему — RimTrans идёт от типов игры, остальные от наблюдений; сверх RimLoc — полнота полей 1.x; ограничения — обслуживание словаря; RimLoc сильнее? — архитектура словаря уже есть, вопрос наполнения; вердикт — **adopt schema, reject код**; лучше? — да: вендоренный словарь + наш dot-path движок.
- *A2*: RimTrans честно портирует `Verse/XmlInheritance`; сверх RimLoc — Class и кросс-мод; ограничение — load-order; RimLoc сильнее — внутри мода да (индексы, env-флаг, тесты); вердикт — **defer cross-mod**; лучше? — при мульти-корне да: инкрементальные индексы вместо полной загрузки.
- *A3*: PathNode/хэндлы RimTrans — самая точная модель ключей; сверх RimLoc — хэндлы для `li` без атрибутов; RimLoc сильнее — в детерминизме записи; **combine**.
- *A4*: chain-фоллбек — adopt; остальное parity.
- *A5*: Strings — implement; RimLoc будет лучше PO-гранулярностью.
- *A6*: три стратегии (исполнить/отказаться/вывести) — RimLoc выбрал третью и это правильный компромисс; **keep**.
- *A7*: фильтры — крупнейший пробел сканера; **adapt** в единый `ExtractionFilter`.

**Цепочка владения (ключевая находка):** `OW` = **OliveWizard**; GitHub-организация переводов — **OneCodeUnit**; git-remote изученного клона RimLangKit — `git@github.com:OneCodeUnit/RimLangKit.git`; README RimLangKit: «от создателя … проекта переводов модов Vanilla Russian Expanded»; .NET AppData-автор — `OliveWizard`. То есть **RimLangKit — инструмент того же автора/команды, что делает OW.RU.***.

**Вывод (с уровнями уверенности):**
1. Переводы сделаны **людьми** (качество, единая терминология на 55 пакетов, Discord-сообщество) — **определённо**.
2. Технический конвейер — **RimLangKit (почти наверняка)**: совпадение автора/организации + байт-паттерны всех его процессоров (EncodingFixer, CommentInserter, CaseCreator, FileFixer, ChangesFinder) покрывают каждый наблюдаемый артефакт. Рабочий процесс восстанавливается так: скопировать EN-дерево → `InsertComments` (EN-комментарии из ещё-английских значений) → перевод значений вручную → `EncodingFixer` (нормализация) → `CaseCreator` (WordInfo) → `ChangesFinder` после апдейтов мода.
3. RimTrans/Text-grabber — **следов нет**; rimworld-autonomous-translator — кода нет, обсуждать нечего.
4. Чего доказать нельзя: байт-уровневое происхождение конкретных файлов ( Workshop-версии могли правиться вручную после генерации; `modVersion 16.03` — своя нумерация релизов). Генерация WordInfo вручную теоретически возможна, но при объёме корпуса маловероятна — Morpher-конвейер CaseCreator для этого и существует.

**Практическое следствие для RimLoc**: целевой формат вывода = **формат этого конвейера** (BOM+CRLF+2 пробела+`<!-- EN: -->`+WordInfo/*.txt+`// defType`), потому что это формат, в котором реально живут крупнейшие русские переводы; совместимость по байтам даст RimLoc безболезненный diff/merge с ними и источник TM+глоссария (см. G3).
