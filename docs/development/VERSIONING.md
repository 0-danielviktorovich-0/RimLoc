# VERSIONING — источники версии и каноническая схема

Дата: 2026-09-27 · Область: все места, где живёт номер версии продукта; правило синхронизации.
Статус: **аудит + схема**. Манифесты в этом документе НЕ менялись — унификация значений (V1) — отдельное решение владельца.

## 1. Источники версии (полный обход репозитория)

Версии в `docs/en|ru/` не обнаружены (grep `0.1.0` — пусто вне `docs/development/`), MkDocs-навигация версий не содержит.

## 2. Найденные несоответствия

| # | Несоответствие | Следствие | Как разрешается |
|---|----------------|-----------|-----------------|
| I1 | CHANGELOG заявляет релиз `[0.1.0] - 2025-09-25`, но тега `v0.1.0` не существует и CLI остаётся `0.1.0-alpha.1` | «Релиз», которого нет: сравнение-ссылка `v0.1.0-alpha.1...v0.1.0` в CHANGELOG ведёт в никуда | Решение владельца: **(a)** материализовать 0.1.0 (бамп + тег, см. §3) либо **(b)** понизить запись до Unreleased. До решения запись не трогать |
| I2 | CLI `0.1.0-alpha.1` «старше» библиотек `0.1.0` (обычно продукт ≥ своих библиотек) | semver-история крейтов путаная; `cargo semver-checks` сверяется с crates.io-версиями, а не с продуктом | закрывается унификацией (§3, правило R1) |
| I3 | Версия GUI дублируется в двух файлах (V3 и V4), равенство ничем не проверяется; несовпадение ломает bundler/updater-логику | рассинхрон возможен тихо | правило R2 + чек-лист перед тегом (§4) |
| I4 | `release-plz.toml`: `shared-version = false`, теги вида `{{package}}-v{{version}}`, `changelog_update = false` — автоматизация per-crate, а не продукта; при этом рабочие релизные workflows «припаркованы» (9591f4f) | release-plz при запуске наплодит per-crate тегов, не создав продуктовой версии и не обновив CHANGELOG | правило R4: до решения владельца release-plz не запускать; продуктовый тег — только вручную по §3 |
| I5 | dev-теги (`v0.0.1-dev.<sha>`) генерировала удаrgенная/отсутствующая dev-автоматизация (в `scripts/` и `.github/workflows/` скрипта dev-релиза нет) | историческая схема тегов без живого генератора | задокументировано в §3 как legacy; новые dev-теги — по схеме §3 |

## 3. Каноническая схема (рекомендация, код не тронут)

**Один номер версии продукта** `X.Y.Z[-pre]` для CLI и GUI. Продукт один, пользователю неважно, что внутри 16 крейтов.

**R1 — значения.** При релизе в ОДНОМ коммите меняются: V1, V2 (все крейты — то же число), V3, V4, V5. V6 не меняется никогда (производное). Значения обязаны совпасть посимвольно (включая pre-release суффикс).

**R2 — соответствие пар.** `V3 == V4` жёстко (Cargo-крейт и bundle-манифест одного приложения); `V5` следует за продуктом (About-карточка показывает версию бандла через V6→V5 — допустимое расхождение только между релизами, не внутри одного).

**R3 — тег.** Единственный материализатор релиза — тег `v<X.Y.Z>` от main (аннотированный). Pre-release в номере (`-alpha.N`, `-rc.N`) — легитимные продуктовые теги; dev-снимки остаются в legacy-форме `<base>-dev.<sha>` и продуктом не считаются.

**R4 — автоматизация.** `release-plz` (per-crate, `changelog_update=false`) несовместим с продуктовыми релизами по R1–R3: запускать только если владелец сознательно переведёт его в `shared-version = true` и включит ведение CHANGELOG. До того — ручной релиз по §4. Парковка release-workflows (9591f4f) этому не противоречит.

**R5 — CHANGELOG.** Пополняется по ходу работы в `## [Unreleased]` (проверяет workflow `changelog-check` на PR). При релизе: `[Unreleased]` → `[X.Y.Z] - YYYY-MM-DD`, снизу создаётся пустой `[Unreleased]`, обновляется блок ссылок внизу файла.

## 4. Чек-лист перед тегом (если владелец решает материализовать 0.1.0 / следующий релиз)

```bash
# 1. Все пять источников совпадают с целевым X.Y.Z[-pre]:
grep -H '^version' crates/rimloc-cli/Cargo.toml crates/*/Cargo.toml \
  gui/tauri-app/src-tauri/Cargo.toml | sort
grep -n '"version"' gui/tauri-app/src-tauri/tauri.conf.json \
  gui/tauri-app/frontend-v2/package.json
# 2. Лок отражён:
cargo metadata --format-version 1 >/dev/null   # свежий Cargo.lock без правок руками
# 3. CHANGELOG: Unreleased переименован, ссылки внизу добавлены
# 4. cargo build/test/fmt/clippy — зелёные (политика AGENTS.md)
# 5. Тег от main: git tag -a vX.Y.Z -m "RimLoc vX.Y.Z"
```

Автоматическую проверку равенства (шаги 1–2 как CI-джоб) можно добавить позже — это изменение кода CI и здесь не выполнялось.

## 5. Что НЕ сделано в этом аудите (осознанно)

- Бамп версий до единого числа (V1–V5) — решение владельца (I1: материализовать 0.1.0 или откатить запись CHANGELOG).
- Перевод `release-plz` на `shared-version`/`changelog_update` или его отключение (R4).
- CI-джоба равенства версий — кандидат в будущую задачу.
