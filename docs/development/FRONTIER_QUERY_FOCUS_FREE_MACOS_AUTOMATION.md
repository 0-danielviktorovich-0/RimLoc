# Запрос фронтир-модели: фоновая GUI-автоматизация macOS без кражи фокуса

Дата: 2026-09-30. Статус: ядро уже решено самостоятельно (см. «Что уже
работает»); фронтир нужен для оставшихся вопросов. Отвечай жёстко по
фактам, спекуляцию помечай явно — это инженерный запрос, не брейншторм.

## Контекст

- macOS 27 (darwin 27, arm64), владелец работает за машиной параллельно с
  агентом-тестировщиком.
- Объект: десктоп-приложение Rust/Tauri 2 + Svelte 5 (WKWebView), release-
  сборка, установленная в /Applications. Мы контролируем исходники — можем
  добавить в приложение всё, что скомпилируется.
- Задача: агент гоняет E2E-сценарии в ЖИВОМ release-приложении, пока
  владелец работает в других окнах. Любое переключение Space/фокуса
  запрещено владельцем.

## Что уже работает (проверено живьём, 2026-09-30)

1. Запуск прямым бинарем с env (`RIMLOC_AUTOMATION=1`) — окно создаётся
   БЕЗ кражи фокуса.
2. Одна короткая активация (~1.5 c) материализует web-AX-дерево
   (AXWebArea; в приложении включены `AXManualAccessibility` на WKWebView,
   App Nap opt-out, фоновый парк-поток self-query AX). После возврата
   фокуса владельцу дерево живёт в фоне ≥90 c простоя.
3. Фоновые `AXUIElementPerformAction(AXPress)` по web-элементам —
   работают без активации (кадры меняются, frontmost владельца не
   трогается).
4. Кадры: `screencapture -x -l<windowid>` — фоновое окно, любой Space.
5. UI-логика/вёрстка гоняются вообще без GUI-приложения: headless
   Chromium + Playwright против vite dev-сервера.

## Что уже НЕ работает (проверено)

- System Events `keystroke` — требует frontmost, крадёт фокус (причина
  инцидента).
- `CGEventPost` клики по координатам — не доставляются.
- `tauri-driver` (WebDriver) — на macOS мёртв (только Windows/Linux).
- `AXWindows` у фонового приложения — пуст (окно доступно только через
  `kAXFocusedWindow`/`kAXMainWindow`).
- `AXUIElementCopyElementAtPosition` — видит только верхние окна.
- Web-AX-дерево БЕЗ хотя бы одной frontmost-активации — не публикуется.

## Вопросы

1. **Нулевая активация.** Можно ли материализовать web-AX-дерево WKWebView
   без единой frontmost-активации приложения? Кандидаты, которые стоит
   оценить: программная `NSApp.activate`-семантика без переключения Space
   (`activateIgnoringOtherApps` в 2025+ депрекейт-статус?),
   `AXUIElementSetMessagingTimeout`, подписка `AXObserver` ДО создания
   окна, приватный `WKWebView _setRemoteInspectionEnabled`-стиль хуков.
   Известные тебе рабочие связки на macOS 26/27?
2. **Живучесть моста.** Web-AX-дерево фонового WKWebView: известны ли
   условия отмирания (часовые прогоны, memory pressure, перерисовка
   страницы) и лучший keepalive? Внешний poller-клиент vs внутренний
   self-query поток — что стабильнее?
3. **Remote Inspector как замена AX.** Для WKWebView в release-сборке
   (мы контролируем билд): публичный/полуприватный путь включить
   WebKit Remote Inspector и подключиться к нему программно (CDP-подобный
   протокол) для DOM-автоматизации вообще без AX? `webView.inspectable`
   (macOS 13+) даёт только Safari UI; известны ли обратные реализации
   RemoteInspector-протокола (аналог ios-webkit-debug-proxy для macOS),
   живые в 2026?
4. **Фоновый ввод.** Ввод текста и scroll в фоновом окне: `AXSetValue` на
   web-input + `AXUIElementPerformAction` scroll-действий — ловушки?
   Или единственный честный путь — инжект в DOM (вопрос 3)?
5. **Слепые зоны.** Что ещё официально поддерживается Apple для
   «GUI-тестирования приложения, пока пользователь работает» на macOS
   26/27, что мы упустили? (XCUITest активирует приложение — не подходит.)

Формат ответа: по каждому вопросу — «сделай так / невозможно потому что /
вот три варианта с ценой». Ссылки на документацию Apple/WebKit и живые
проекты приветствуются; выдуманные API помечай как гипотезу.
