# BETA TEST CHECKLIST — RimLoc RC

Два разных чек-листа:

- **Часть I — обычный тестер.** Вам нужен только готовый артефакт приложения (`RimLoc GUI.app` / `.dmg` от владельца). Rust/npm/git **не нужны**. Пути выбираются нативным диалогом выбора папки — вручную набирать пути не требуется.
- **Часть II — разработчик/адверсариальный.** Всё, что ломает данные, делается ТОЛЬКО на одноразовых копиях (см. правило ниже).

**Уровни поддержки платформ (точно):** macOS — собран, запущен, workflow-проверен автоматически; человеческая проверка = этот чек-лист. Windows/Linux — сборка в dev-конфигурации; человеком НЕ проверялись; сообщения о багах приветствуются.

---

## Часть I — обычный тестер (macOS, 30–45 минут)

### 0. Установка
- [ ] Получить артефакт: `RimLoc GUI.dmg` → открыть → перетащить «RimLoc GUI» в Applications → запустить (при первом запуске неподписанной сборки macOS спросит подтверждение — это ожидаемо для тестовой сборки).
- [ ] Приложение открывается; экран Home живой.

### 1. Первый проект
- [ ] «Новый перевод» → выбрать папку мода через **диалог выбора папки** (любой мод из Workshop — приложение читает его только для чтения и ничего в нём не меняет).
- [ ] Скан находит записи; проект появляется в «Недавних»; после перезапуска приложения открывается из списка.

### 2. Перевод
- [ ] Открыть запись, ввести перевод. Закрыть и заново открыть приложение — черновик на месте.
- [ ] Сохранить — счётчики обновились. На очень больших модах (10k+ записей) сохранение может ощущаться до ~0.1 s — это нормально.

### 3. Проверка проекта
- [ ] «Проверить проект» на корректном переводе — «Ошибок нет».
- [ ] Эксперимент на копии: удалить `{0}` из перевода → проверка показывает ошибку «потерян плейсхолдер», клик ведёт к записи.

### 4. Экспорт и сборка мода
- [ ] Экспорт: нажать выбор папки и указать любую СВОЮ папку (например, новую папку в Документах) → «Записано и перепроверено», файлы существуют.
- [ ] Сборка мода: указать новую пустую папку → получить пакет перевода; при желании положить в копию мода и проверить в игре.

### 5. Диагностика и отчёт об ошибке
- [ ] «Полная диагностика» → «Собрать бандл» → папка с `report.md` и диагностикой (без паролей и личных путей).
- [ ] Справка → «Подготовить отчёт» → превью содержимого → сохранить.

### 6. Если что-то пошло не так
- Приложение показало ошибку текстом — сфотографируйте/перепишите её.
- «Полная диагностика» → «Собрать бандл» → приложить к сообщению вместе с описанием шагов. Лог: `~/Library/Application Support/RimLoc/logs/gui.log` (папка открывается кнопкой «Открыть логи» в настройках).

## Часть II — разработчик / адверсариальный (только одноразовые копии!)

> 🔒 **Железное правило:** каждый тест из этого раздела выполняется на **копии** мода/проекта во временной папке (`/tmp` или новая папка). Оригинальные моды Workshop, установленная игра и сохранения — только для чтения, НИКОГДА не модифицируются. Управление через CLI: `rimloc-cli --help`.

### A. Валидация на сломанных данных (копия мода)
- [ ] Дубликат ключа в Keyed-копии → validate: дубликат виден.
- [ ] Битые плейсхолдеры (`{0]`, незакрытый `{`) → validate: ошибки, export/build отказывают или предупреждают согласно severity.
- [ ] Невидимые/bidi-символы в ключах → warning.

### B. Гварды записи
- [ ] Относительный `out_dir` в GUI-поле → типизированный отказ (`invalid_output_path`) ДО любых fs-операций.
- [ ] Абсолютный путь ВНУТРЬ исходников мода → отказ (containment).
- [ ] Symlink out_dir, ведущий внутрь исходников → отказ (тест `symlink_out_dir_into_source_tree_is_denied`, проверить руками на копии).
- [ ] Export/build в несуществующую папку → корректное сообщение, мусор не создаётся.
- [ ] Legacy-поверхность (`RIMLOC_LEGACY_COMMANDS=1`): write-команды с относительными путями теперь ОТКАЗЫВАЮТ (было: тихая запись относительно CWD).

### C. Сессии и конкурентность (копии проектов)
- [ ] Изменить файл проекта на диске извне → «Сохранить» в GUI → баннер «изменён извне» → «Принять версию на диске» → сессия перезагружается, приложение живо.
- [ ] Битый (обрезанный) JSON проекта → список проектов не падает, файл числится unloadable, байты файла не тронуты.
- [ ] Два инстанса приложения на одном проекте → disk-hash защита: второй получает typed `project_changed_on_disk`, а не тихую перезапись.
- [ ] Re-parse после краша: недописанный файл невозможен (tmp+rename); открыть существующий проект 3 раза подряд → байт-стабильность.

### D. Ядро/автоматизация (по желанию)
- [ ] `testlab/ui_automation` stage-split journey на dev-сборке (README модуля); на release-артефакте — только короткий ручной прогон Части I.
- [ ] `examples/perf_bench.rs` в release: apply batch=100 ≈ 50 ms на 15k записей.
