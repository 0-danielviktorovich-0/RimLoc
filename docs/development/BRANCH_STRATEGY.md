# BRANCH STRATEGY — ветвление на основе фактического состояния

Дата: 2026-09-27 · Статус: **документ-рекомендация**. Ветки этим документом не создавались и не переименовывались.
Связанное: [VERSIONING.md](VERSIONING.md) (тег релиза от main), CI-гейты (`.github/workflows/`).

## 1. Фактическое состояние (evidence, 9591f4f + bf86f57)

| Факт | Доказательство |
|------|----------------|
| trunk-based: main — единственная длинная ветка, разработка приезжает волнами | история: интеграции волн merge-коммитами (`chore(gui): integrate W6 … (codex/w6-demo 3d60cfb)`, `…(codex/w7-source 18b9d28)`) |
| короткоживущие рабочие ветки с префиксом `codex/<slug>` | 11+ веток: `codex/w6-demo`, `codex/w7-source`, `codex/backend-integration`, `codex/gui-integration`, `codex/rc-corpus`, `codex/rc-provenance`, `codex/w45-ux`, `codex/built-gui`, `codex/pass-b-tails`, `codex/night-ui-fixes`, … |
| параллельные сессии работают в отдельных git-worktrees | `Developing/_rimloc-worktrees/` — 7 рабочих деревьев, у каждого своя ветка |
| CI-гейты висят на PR, не на пушах | 8 workflow в `.github/workflows/`: `ci` (PR + еженедельный schedule + dispatch), `changelog-check` (PR→main), `semver` (PR→main), `public-api` (PR→main), `schema-check`, `docs` (PR), `publish` (только dispatch), `release-plz` (dispatch + PR) |
| push-триггеры сняты | b102f3e «ci: disable push triggers, keep manual dispatch» |
| релизные workflows припаркованы решением владельца | 9591f4f «ci: park release workflows (owner decision)» |
| docs-only правки идут прямо в main | прецеденты: 827aca0, 92ba176, 05ba9f6, bc1a934 |
| нестабильные снимки уже покрываются dev-тегами, а не веткой dev | теги `v0.1.0-alpha.1-dev.<sha>`, `v0.0.1-dev.<sha>` |

## 2. Варианты

| | A. Trunk-based + короткие ветки (текущее) | B. main + долгоживущий develop (git-flow lite) |
|---|---|---|
| стоимость интеграции | одна — PR в main | двойная — PR в develop, потом develop→main |
| CI-гейты | срабатывают на каждом PR (уже настроены) | нужно перенастраивать половину workflow (цели веток), гейты на develop дублируют main |
| изоляция нестабильной работы | worktrees + фичевые ветки (уже практика); нестабильность помечается dev-тегами, а не веткой | develop как «полка» нестабильного — но полка уже существует (worktrees) |
| кто поддерживает | 1 владелец + AI-агенты | рассчитан на команду с релизными циклами |
| риск для main | прямой пуш мимо PR остаётся без гейтов до еженедельного прогона (push-триггеры сняты) | тот же риск + рассинхрон main/develop |

Вывод: для этого репозитория (один владелец, агентские волны, уже работающие worktrees и PR-гейты) вариант A строго дешевле и уже оплачен практикой. Вариант B добавил бы вторую очередь интеграции без единой новой гарантии.

## 3. Рекомендация (фиксация текущей модели)

**Trunk-based. main — всегда релизопригоден. Код — только через короткую ветку + PR.**

| Поток | Правило |
|-------|---------|
| Код (crates/, gui/, скрипты) | ветка `<runtime>/<slug>` (де-факто `codex/<slug>`; новый рантайм — свой префикс) → PR в main → гейты (`ci`, `changelog-check`, `semver`, `public-api`, `schema-check`, `docs`) → merge-коммит с ссылкой на ветку и sha (текущий стиль `integrate <wave> (branch sha)`) |
| Срок жизни ветки | дни; волна интегрирована — ветка удаляется (зависшие `codex/*` с уже влитой работой — кандидаты на чистку владельцем) |
| Параллельные сессии агентов | отдельный worktree на ветку (`Developing/_rimloc-worktrees/<slug>/`) — текущая практика, обязательно при одновременных волнах |
| Docs-only и CI-хозработы | допустимы прямо в main (прецеденты выше); правило из AGENTS.md «не заканчивать с незакоммиченными правками» действует |
| main | force-push и rewrite истории запрещены; прямые push коммитов кода — избегать: при снятых push-триггерах они не проходят гейты до еженедельного schedule-прогона |
| Релизы | тег `vX.Y.Z` от main по чек-листу VERSIONING §4; релизные workflows включаются владельцем dispatch'ем (парковка 9591f4f остаётся в силе до его решения) |
| Нестабильные сборки | dev-теги `<base>-dev.<sha>` (legacy-схема), отдельная ветка dev не заводится |

## 4. Открытые вопросы владельцу

1. Чистка зависших веток `codex/*`, чья работа уже влита в main (список в §1) — удалить или оставить как метки истории.
2. Возвращать ли push-триггеры на main хотя бы для `ci` (быстрая обратная связь на docs/хоз-коммиты) или оставить модель «гейты только на PR + weekly».
3. Судьба `release-plz` — см. VERSIONING §3 R4 (несовместим с продуктовыми релизами в текущей конфигурации).
